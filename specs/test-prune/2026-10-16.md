**The kind of mistake to watch for in the cleanup.** One claim in twenty was refuted and seven needed an assertion moved. Every miss had the same shape: "Y covers X because Y checks something similar", without checking that Y's data ever reaches X's edge case. The cleanup therefore proves each "covered by" before the test goes:
- **Unit and integration tiers:** run mutation testing on the module (StrykerJS, Stefan's suggestion), with and without the test. If the mutation score stays the same, the DELETE is safe. If a mutant now survives, the test, or its assertion, moves instead.
- **E2E:** break the behaviour by hand, run the covering test, and see it go red before the old test is deleted.

## Rulings (Stefan, 2026-10-16)

His words: "1 completion, 2 remove, 3 collapse, 4 yes".

1. **Completion.** A step's browser acceptance tests are a completion criterion. A gate test whose behaviour a cheaper tier now pins can go, test by test:
   - each removal is proven, by mutation or by a hand-broken check;
   - its CHECKS row and plan cell are edited in the same commit;
   - every SPEC acceptance line that names a browser flow keeps at least one e2e.
2. **Remove** the dead production code with its tests: the site's own words, the time kind, the four unserved field types, the prefs stub and ViewPanel.
3. **Collapse** the smoke checks to one sign-in-page check, the record-link headers check and one API probe. Also propose the netdust-gates lesson.
4. **Yes** to mutation testing: StrykerJS, report-only first, as its own unit. It is the arbiter for the "covered by" claims.

## Questions only Stefan can answer (answered above)

1. **Are a step's browser acceptance tests permanent?** This decides about 120 of the 169 conflicts and about 8 minutes of gate. These are the step-0a–3f gate specs, registered in CHECKS.md and named in plan Test maps.
   - SPEC:345 and AGENTS.md say "a step is done when its acceptance gate passes in a real browser".
   - Read as a **completion criterion**, a gate test whose behaviour a cheaper tier now pins can go. Its CHECKS row and plan cell are edited at the same time.
   - Read as **standing**, they stay, and the gate time comes from the helper changes only.
   - My recommendation is the completion reading, test by test. Each delete is proven by the hand-broken check above. The SPEC acceptance lines that name a browser flow (SPEC:349, :351, :352, :353, :354) keep at least one e2e each.
2. **Dead production code.** Remove it with its tests, or keep it? AGENTS.md says "not stubbed, not prepared for", so I'd remove all of it, in the UI-architecture feature:
   - the site's own words (`setStrings`, `Schema.strings`, the `refusals` branch of errorText), from the WordPress era;
   - the time kind (columns.ts:109, cells/Time.tsx, toTime/fromTime), which only the fixtures reach;
   - the field types `email`, `url`, `html` and `image`, which the adapter never produces;
   - the `prefs`/`savePrefs` stub;
   - `ViewPanel.tsx` and its CSS, which nothing imports.
3. **Smoke checks in a repo with no deployed environment.** 47 @smoke tests run inside the gate on the same fresh instance (CHECKS.md:3-5). The shake-out adds one per feature. Most are the same session check, or the same sign-in page under a different hash (E1).
   - My recommendation: one sign-in-page smoke test, plus the record-link headers test, plus one API probe.
   - This is also a harness lesson for netdust-gates: a repo with no deployed environment gains nothing from a @smoke check per feature.
4. **Mutation testing.** Add StrykerJS as its own small unit after 3f, report-only. It runs first on the modules where the DELETEs cluster (grid store, group, columns, board rank and drop, the engine filter compiler and validate) and then serves as the arbiter for the "covered by" claims above. The grid's Vitest runner fits Stryker; bun test needs Stryker's command runner, which is slower.
