## How to read it

- **Engine tests only.** filter-compile.ts, filter.ts and validate.ts are judged by packages/engine/test alone.
  - Theatre and fiche tests import the unmutated `@worktable/engine`, so they cannot kill an engine mutant.
  - This report is therefore the arbiter for the T slice's "the engine already pins it": the engine pins a behaviour only if an engine test kills its mutant.
- **No type checker.** No checker plugin runs.
  - A mutant that would not compile still runs, and it mostly dies at runtime, which raises the scores a little.
  - `tsconfigFile` points at a file that does not exist, because Stryker's tsconfig preprocessor calls `ts.parseConfigFileTextToJson`, which TypeScript 7 lacks.
- **The grid runner is patched.** @stryker-mutator/vitest-runner 10.0.0 joins test names with `' '` to build each mutant's name filter. Vitest 5 joins them with `' > '`.
  - Without the patch, every covered mutant ran zero tests and survived: rank.ts scored 0.9% unpatched and 78.6% patched.
  - The patch in `patches/` changes the join. upstream-issue.md has the upstream issue (#6210), the fix (#6214), and when we drop the patch.
- **The engine runner sees no tests.** The engine runs through Stryker's command runner, `bun test --bail`.
  - Every mutant runs the whole engine suite.
  - There is no per-test coverage, so "No coverage" is always 0 for the engine. There is no killedBy either.
  - Incremental mode cannot see an engine test change, so `bun run mutation` forces an engine module when packages/engine/test changes.
- **Static mutants.** A grid mutant in code that runs at import, outside any test, is static.
  - A static mutant runs every related grid test. Incremental mode reuses its result without knowing whether those tests changed.
  - columns.ts has 236 static mutants. store.ts has 3, group.ts 6, rank.ts 1 and drop.ts 1.

## Timeouts

In the first pass, 100 mutants timed out: 73 in columns.ts, 1 in rank.ts, 9 in filter.ts and 17 in validate.ts.

- **columns.ts.** All 73 are static.
  - **Why they overran:** a static mutant runs all 913 of columns.ts's related tests.
    - Stryker sets a mutant's limit from the dry run, which ran alone: net time × 1.5 + 5 s + overhead.
    - In the first pass that came to about 172 s: a net 72 s plus a 59 s overhead.
    - The mutant runs went four at a time, each a full suite. A passing one overran that limit, most likely through contention between the four.
    - With the recheck's 60 s, the limit for a static mutant is about 294 s (a net 100 s plus an 84 s overhead), and every one finished.
  - **Not load:** the 73 accrued at a steady rate from minute 14 of the module's run to its end, with no rise during laika's 00:09–00:14 gate.
- **filter.ts and validate.ts.** None of the 26 is static.
  - **They match laika's gates:** by the progress log (±1 min), 7 of filter.ts's 9 fell inside laika's 00:38–00:43 gate. 12 of validate.ts's 17 fell inside its 01:01–01:06 and 01:32–01:37 gates.
  - **Why load causes them:** the command runner's limit is about 31 s for a 17 s suite (no overhead). A 10-worker Playwright run beside it can push a passing suite past that.
  - **Not concurrency alone:** filter-compile.ts ran the same four-at-a-time on a quiet box and had none.
- **rank.ts.** Its one timeout is genuine, so it was not rerun.
  - The mutant at rank.ts:30 turns `while ((a[n] ?? FIRST) === b[n]) n++` into `!==`, which never ends.

**The recheck.** It reran those mutants with `timeoutMS: 60000`, incremental off.
- **When:** 2026-10-17 09:46–10:32 for columns.ts and 10:32–10:36 for the engine. The box was quiet: a 5-second watch saw no Playwright, phpunit, composer gate, `ddev exec` or `ddev wp` process for the whole run.
- **Scope:** its mutate ranges also took in nearby mutants that had not timed out: 75 in columns.ts. All 75 came back as the first pass had them.
- **Consistency:** a first recheck pass, 01:50–02:03, covered 67 of the same columns.ts mutants and agrees on 66. The 67th timed out again there and survived on the quiet box.

**The config change.** Both stryker.config.json files now carry `timeoutMS: 60000`, so a rerun reproduces these numbers.
- **The new limits:** about 294 s for a static columns.ts mutant and about 87 s for an engine run.
- **Headroom:** the margin under load is not measured, so a loaded box can still turn a survivor into a timeout.
- **When it matters:** before a removal hinges on a module, rerun that module on a quiet box, as the cleanup brief says.
- **The cache still holds the first pass.** The first pass's 99 timeouts that the recheck changed are still cached as timeouts.
  - They sit in `reports/mutation/<slug>.incremental.json` in the feature/mutation-testing worktree (gitignored).
  - Incremental mode reuses a cached result, so a rerun there would report them as timeouts again.
  - Before rerunning a module, delete its `<slug>.incremental.json`, or run from a fresh worktree, which starts with no cache.
