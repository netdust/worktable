# Advisor review of `specs/step-2/plan.md` (e0fbf4f): does the plan carry the findings?

Read-only, 2026-10-09. Checked against `specs/step-2/findings.md` (40d91ed), my `f1-f2.md` draft, `review-findings.md` and `plan-facts.md` §6. Line numbers are `plan.md`'s unless prefixed.

## Blocking

**B1. The e2e engine starts before the secret file exists (plan.md:339).** Task 10 says `--link-secret-file e2e/.tmp/link-secret`, "written by global setup". Playwright starts the web servers first and runs `globalSetup` once they are up (`playwright.config.ts:7` says so in its own comment). Task 9 makes `serve.ts` refuse to start when the domain declares `record_link` and the file is missing, and Task 10 makes theatre declare it, so from Task 10 on the theatre engine never comes up and every e2e flow fails. Write the file inside the webServer command (`sh -c 'mkdir -p e2e/.tmp && [ -s e2e/.tmp/link-secret ] || head -c 32 /dev/urandom > e2e/.tmp/link-secret; bun … --link-secret-file e2e/.tmp/link-secret'`), or commit an invented test secret under `e2e/` with a line in the plan saying why that one may live in git.

**B2. "Two concurrent `/act` calls on one row give one 200 and one 409" cannot happen with one token (plan.md:203, 113 "simultaneous-confirm-409"; findings.md:207 has the same flaw).** The token is consumed on first use (`UPDATE … WHERE used_at IS NULL`, findings.md:179), so the second call with the same token is the identical `401 bad_token` of attack 1, never a 409. A 409 `transition_lost` needs two different callers stating `expect`: the planner's `PATCH { state: 'bevestigd', expect: { state: 'uitgenodigd' } }` racing the person's `POST /act`, or two tokens on one row. Name the pair in Task 3's test and in Task 8's e2e flow, and add one line: the consume and the transition run in one transaction, so a 409 rolls the `used_at` back and the token stays usable (a declined-after-confirmed should answer "al bevestigd", not burn the link).

**B3. The matrix's own undo will 422 on every state change once Task 4 lands (plan.md:215, 271).** The matrix store reverses a cell edit by re-sending the previous content as a new `PATCH` of `state` (`store.ts:352-370`, `changed()` at `:151-157`). With the lifecycle, `bevestigd → uitgenodigd` is undeclared, so Ctrl+Z in the matrix answers 422 `transition_not_allowed`, and the existing matrix undo tests (vitest `store.test.ts`, the step-0d/0e e2e flows) fail at Task 4 Step 4, which the plan expects to pass. plan-facts §6.9 said this for actions; it holds for plain cell edits on a lifecycle column too. Decide in Task 4: a state edit in the matrix is undone through the batch history (`App.tsx:176`), like the fill in Task 7, and the op stack keeps only note edits; or the matrix sends `expect` and the undo re-sends the inverse with `expect`, which still needs the inverse to be declared. The first is the one that matches findings F3 ("undo makes the exact inverse… in undo mode"). Also: the matrix store's `changed()` must send `expect` with the shown status, not only the grid's cell (Task 4 names `Grid.test.tsx` only).

## Should fix

**S1. Task 3's `/act` needs a fixture with an owner column, and the subject derivation is unstated (plan.md:159, 190, 194).** `linkAccount(sqlite, subject)` needs `{ dataset, id }`; `/act` runs "as `linkAccount(owner of the record)`", which is `subject = { dataset: columns[owners.owner].relation ?? dataset.name, id: row[owners.owner] }` (`id` as owner column means the row itself). Task 2's `ticket` fixture declares no `owners`, so Task 3 cannot test `/act`, the scope guard of attack 2, or `whose()`'s subject title. Give the lifecycle fixture `owners: { owner: 'member_id' }` with a `member` dataset (as `test/matrix.test.ts:20` does), and write the derivation into Task 3's interface. `checkSubject` (`auth.ts:60-71`) will then verify the subject row is live.

**S2. `token_projection` "owner-visible only" cannot be validated before Task 9 (findings.md:182; plan.md:162, 193).** `ColumnDecl.owner_visible` arrives in Task 9. Say in Task 3 that validation checks `token_projection ⊆ columns`, and in Task 9 that it also requires `owner_visible` on each, with a test; otherwise the implementer of Task 3 either invents the flag early or drops the rule.

**S3. Where the secret refusal lives decides whether `parity.ts` and `testEngine` keep working (plan.md:309).** Task 9 puts the refusal in `serve.ts`. `scripts/parity.ts:260` and `test/sign-in.ts:15` call `createEngine` directly with the theatre domain, which declares `record_link` from Task 10 on. State it: `EngineOptions.linkSecret?: Buffer`; `createEngine` throws when the domain declares `record_link` and none is given; `serve.ts` reads the file and checks its mode; `test/sign-in.ts` passes a fixed test secret (add it to Task 9's Files); `scripts/parity.ts` passes one too (add to Task 10 or 12, or Task 12's "0 mismatches" run fails on startup).

**S4. Three places in `views.ts`/`seed-missing.ts` that must learn `for_owners` are missing from Task 9 (plan.md:309).** (a) `checkPublishable` (`views.ts:298-304`) must refuse `share-token` on a for-owners view (`already_for_owners`); Task 9 lists only the reverse. (b) `DELETE /views/:id` clears `public` and the token (`views.ts:273`); it must clear `for_owners` too, or a restored view is still owner-facing. (c) `--seed-missing` brings system-owned views up to their declaration and leaves public ones alone (`seed-missing.ts:110-130, 159`); a for-owners system view must be left alone the same way, or a later seed can put a non-owner-visible column into `visible_fields` past `setForOwners`.

**S5. Owner accounts and `/owner/views` (plan.md:316; spec R9).** Findings F1 item 6: owner accounts keep what the spec gives them and also get the owner views. Task 9 and R9 speak only of the link actor. State that `owner.views` is allowed to role `owner` of any kind, and test an owner session reading the same list as the link; an editor session is 403.

**S6. The 60/min read limit on `/owner/*` is nowhere in the plan (plan.md:64, 67, 323).** The findings' defaults (findings.md:261) name 60 per address per minute on owner reads, failing closed, beside the 20 failed authentications per 15 minutes. Task 9's "429 after the limit" and attack 8 mention only the second. Name both, and which limiter key each uses.

**S7. Threat model gaps.** (a) F2's attack 8, OpenAPI as reconnaissance, is missing: add it with its mitigation (generated under the caller's `readable()` filter; a link actor is 403) and its Task 11 test. (b) Attack 2 names `runTransition`, which no task produces; the scope check is `currentOf` in `runWrite` (`writes.ts:357-362`), reached because `/act` calls `runWrite` as the link account. (c) Attack 16 names rotate/disable and the per-account limit but not the per-address failure limit on bad Bearers (Task 11 tests it); add it to 16 or 17.

**S8. The natural-key seed can never deliver a slotted "speeldag" to a database that already holds one (plan.md:254, 261; spec R7).** The natural key is the title, and the rule is never update. A database that already has "speeldag op locatie" (unslotted) keeps it. The real database is fine: step 1's real-data run migrated a copy and never ran `--seed-missing` on it (`specs/step-1/task-7.md:23`), so step 2's run inserts both Rol and the slotted Sjabloon. But Task 6's test "an existing db with Rol and an older Sjabloon … inserts the missing slotted speeldag" only holds if the older one has another title. Say so in the test, and put the general case in `real-data.md`: a database with an unslotted "speeldag op locatie" keeps it, and the planner adds slots by hand (Sjabloon is create-only today, `writers.ts:272-279`, so by copying).

**S9. The Mailer and the app URL must reach `runWrite`/`runAction`, which hold `Store`, not `c` (plan.md:149, 159).** Task 1 says Tasks 2, 8 and 9 send through `c.get('mailer')`; Task 2's post-commit mail runs inside `writes.ts`/`actions.ts`, which get `Store` (`writes.ts:30-34`, built at `app.ts:163`). Put `mailer` and `appUrl` on `Store` in Task 1, and say in Task 2 who builds the `#/act/<token>` link that `HookResult.mail(link)` receives: the engine, from `appUrl` and the raw token Task 3 mints.

**S10. The minted token's `from` is the hook's own state (plan.md:191, 293).** The hook fires on the move *to* `uitgenodigd`; the token it asks for acts *from* `uitgenodigd`. `mintActionToken`'s `from` is therefore the transition's `to`, and `batch` is the write's key (`writes.ts:382`, created before the write). One sentence in Task 3 prevents the obvious bug of minting with the transition's `from`.

**S11. `expect` must survive the grid's body mapper (plan.md:215).** `toEngineData` (`apps/grid/src/engine.ts:361-369`) maps every key through `wireValue` against the declared column; `expect` has none, so its object passes through `wireValue(undefined, …)`, which was written for scalars and id lists. Route `expect` around the mapper in `api.update` (`api.ts:154`) rather than through it, and test it.

**S12. `createAccount` cannot make a service or link row (plan.md:190, 357).** `createAccount` runs `emailOf` (`auth.ts:80`), which refuses a missing address. Task 3's `linkAccount` and Task 11's `--create-service` need their own insert; say so, so nobody reaches for `createAccount` and widens `emailOf`.
