# Planning Engine — Architecture

The tool is for admins and their work. Everyone else uses webpages built on the engine's data: they read through queries and published views, and the only writes from outside are the few a page makes for one person through that person's own link or token.

One standalone engine, many domains. The theatre planning model as the first domain. Websites, including WordPress, are REST clients and nothing more.

## What this is

An engine that knows *shapes* — datasets, queries, views, writers, publications — and domain packages that know *names*. Point it at the theatre declarations and it is Laika's planning tool; point it at a fiche declaration and it is a referral guide. The engine never learns a domain word.

The edge over Yesplan, Rentman and Propared is not a feature but the split itself: those products hardcode their entities and bolt registration on as a second module. Here the admin builds views on *computed* data, the person's plan and actual sit on one row, and a new client is a new declaration, not a new product.

Three sources feed this one: the [Laika Planning — Foundation](https://claude.ai/code/artifact/2bfb4337-ea13-4888-975e-dd11da3adf66) doc (the theatre model), a code review of the atelier, ntdst-core and ntdst-baseline repos, and a real Laika planning spreadsheet. This doc supersedes the Foundation doc where they differ. Decided on 4 October after the review: the engine is a standalone service with its own database, not a WordPress plugin. The review showed that building it inside WordPress would spend most of the foundation teaching WordPress's data model a second backend — work that serves no other client and no agent. The theatre data model, the shapes and the contract did not change with that decision; only Storage and step 0 did.

## The layers

Five layers, one direction of dependency: each layer knows the one below it and nothing above.

| Layer | Package | Knows | Never knows |
| --- | --- | --- | --- |
| Delivery | engine | Published views, recipients, share links, the recipient page, ical/pdf renderers | Which domain the rows came from |
| Views | engine | SavedView rows: a source (dataset or query), filters, sort, group, hidden columns, skin, scope | What a column means |
| Engine data | engine (TypeScript service) | Declared datasets and queries as shapes; Field, Revision, Publication, Attachment keyed on ((entity, record_id)); the table store and migrations | Any domain name |
| Domain | theatre package (or any client's) | Its datasets, its SQL views, its writers with the cross-field rules, templates, roles, conflict definitions | How the grid renders or publishes |
| Storage | the engine's own database | Tables for datasets, SQL views for queries, JSON columns for custom fields; SQLite first, Postgres when a client needs it | Nothing above it |

The contract between engine and domain is one registration call per shape — a dataset, a query, a writer — and nothing else. Everything the engine does with a declared shape (migrate its table, render its columns, route its writes, snapshot its rows) it does without reading the declaration's names.

## The engine

The engine is a standalone TypeScript service on the Folio stack (Drizzle, SQLite) with its own REST API, plus the React grid that exists today pointed at that API instead of WordPress. Its TypeScript and React code is copied from ntdst-baseline's views app; no PHP is copied. The grid's UI parts come from React Aria Components; the sheet is the grid's own. The PHP behind the grid — `RowQuery`, `Lookups`, `Rollups`, `Writes` in ntdst-baseline — is replaced, not ported; the review showed it to be a thin wrapper over `WP_Query`. Baseline drops the views module and goes back to hardening. The same REST that serves the grid serves agents and any website that wants a view. `GET /rows/:source` returns at most 5000 rows by default; a requested limit above 5000 is refused with a 400; `offset` pages past it; `total` is an exact count from a separate query, never the length of the page. On the matrix's down source, `cells=1` returns each row with its live join rows; it needs a window of at most 92 days.

The list is the engine's own table declarations. A dataset may declare `links: { name: { label, item, dataset, key, target, state?, count? } }` (`item`: the word for one link; `count`: an integer column of `dataset` holding how many places a link row holds): a column holding the rows of `dataset` whose `key` is this row's id, served on each row as `links: { name: [{ id, target, title, state }] }`, ordered by id, read through the caller's scope on that dataset; `title` is the target's title, or the link row's own title when it has no target; a link with a `count` adds `places` to each item, the row's `count` when that is a positive integer and 1 otherwise, and to an owner only when the `count` column is owner_visible, as a lookup; an item without `places` holds one; `/schema` serves a link only to a caller who can read its dataset, with its `target_dataset` and the state column's options, tones and default. They are written with that dataset's own create and delete. `key` must relate to this dataset, `target` must be a relation column, `state` an options column and `count` an integer column that is not a relation; a link name may not be a column's, and no column may be named `links`. A link is shown and saved in a view like a column, never sorted, grouped, filtered or published. A dataset may declare `lookups: { name: { label, via, field, own?, from? } }`: a column it does not store, holding the `field` of the live row its relation column `via` names, read on every read, so it never goes stale. With `own` (a nullable, writable column of this dataset of `field`'s type and relation, not its lifecycle column or record-link address, and the `own` of no other lookup; `from` is then required) the lookup is inherited: the value is `own` when set, else the related field; `from` is the word for where an inherited value comes from, and each row says which of its inherited lookups came through the relation (`inherited: [name]`). A lookup is filtered, sorted, grouped and saved in a view like a column, and served in `/schema` under `lookups` with its type, options and relation taken from `field`. A write never stores a lookup: a plain one is dropped like a read-only column, and a write to an inherited one is a write to its `own` column, through the writer and the transition check, revised under `own`; null makes it inherit again. `via` must be a relation column, `field` a column of its target that is not json, not boolean and not another lookup; a lookup name may not be a column's or a link's. On a dataset that declares `owners`, a lookup is served to editors and administrators only, and a filter or sort on it is refused under any other scope, so an owner still reads only titles through a relation; a lookup may declare `owner_visible: true` only when it reads the owner's own record: its `via` is the dataset's owner column, its target dataset's owner column is `id`, and its `field` is `owner_visible`; so an owner never reads a field of another owner's record, and only such a lookup may appear in a view for owners. A relation column, or a relation action input, may declare `options_from: { source, match, value }`: its picker lists the `value` records of the rows of the query `source` whose `match` columns (`{ <query column>: <this row's column> }`) equal this row's, in the query's order, read in the caller's scope; `value` must be a relation column of the query to the same target. An optional `sort` (columns of `source`, `-` for descending) is the order the picker reads them in, since the rows route orders by sort and then id, never by the view's own order. The options narrow the picker and never authorise: the writer still judges the value. |

| SavedView | name, source_type (dataset · query; none on a dashboard), source (none on a dashboard), skin (table · calendar · matrix · list · board · timeline · gallery · dashboard), layout (a dashboard's sections, tiles and quick actions; none otherwise), filters, sort, group_by, visible_fields, shared, owner_id, share_token, format (html · ical · pdf), public, for_owners | A saved view is a row; `source_type = query` lets admins build views on computed data. Column widths and the matrix's picked columns stay per viewer in the browser. Known limit until Field (step 5): a saved view cannot keep a hidden column's position, nor custom columns. Every batch is recorded in the engine's `batch` table with its actor and kind (write · action · undo · import · seed). `POST /batches/:id/undo` undoes the caller's own write, action or undo batch in one transaction, through the writers and the caller's scope: a column is restored only while it still holds what the batch wrote, and a record the batch created is removed only while no column it left empty has been filled since; otherwise nothing changes and the answer is 409 `changed_since` naming the column. Redo is undoing the undo batch, under the same rule. An undo back into a hooked state does not re-mint (hooks never fire in undo), and a redo of an undone batch that minted action tokens is refused with 422 `not_undoable`, since the undo revoked its tokens; the grid says "Opnieuw doen kan hier niet" and drops the step. Another account's batch is refused (403); a batch holding a delete is never undone, unless every row in it is an attachment row (undoing a file delete restores the file); an import or seed batch, a batch recorded before the table, and an already undone batch are never undone, files included. | Publication | recipient_type (person · organisation), recipient_id, language, saved_view_id, period_start, period_end, rows (JSON), sent_at, channel, version | The rendered rows a recipient received, names not ids; the diff basis. Deleting a public view revokes it: `public` and the token are cleared with the delete, so a restored view is private and its old link answers 404. While a view is public only an administrator may change it (403 `public_view`). `GET /public/views/:token` needs no session, takes only `from` and `to`, applies the stored filters and sort, and answers `{ columns, rows, total }`, each row projected to `visible_fields` and never the owner column; 60 calls per client address per minute, failing closed; no CORS header. Every visible field and every stored filter, sort and group key must be a column the domain marks `owner_visible`, else 400 naming it; a view is public or for owners, never both (400 `already_public`, `already_for_owners`). While set only an administrator changes it, and a PATCH re-runs the checks; deleting it clears the flag. `GET /owner/views` lists the views for owners the caller can read with their columns' keys, labels and types, and `GET /owner/views/:id/rows?from&to&filter&sort&group` reads one in the caller's owner scope, never unscoped: rows carry only the owner-visible keys (no `id`, `title`, `lookups`, `custom` or `links`), every key the request names in filter (inside `$or` too), sort and group must be owner-visible (`custom.*` refused; 400 `column_not_owner_visible`), and `total` is counted in scope. Both routes are for role `owner`, a link account included, and 403 to an editor or administrator; 60 calls per client address per minute, failing closed |
| Attachment | entity, record_id, kind, name, mime, size, sha256, uploaded_by (built in F1); show_on_publication and inheritance down a declared parent relation come with step 4 | One attachment mechanism for any row of a dataset that declares `attachments`, indexed on (entity, record_id). Files live in the directory `--files-dir` names, created with mode 0700 and backed up with the database, each named by its sha256, never by the uploaded name; the engine refuses to start when a dataset declares attachments and no directory is given. The files' total size is capped by `--files-max-gb` (a positive number, default 5 GiB), the same bytes counted once and soft-deleted files too, since undo needs them (deleted files keep counting until a purge exists): an upload whose `Content-Length` would take the total over the cap is 507 `storage_full` before a byte of the body is read, new bytes that would pass it after stripping are refused the same way with nothing stored, and restoring a deleted file adds nothing. `GET /attachments/:dataset/:id` lists a record's files (`{ attachments: [{ id, kind, name, mime, size, own, created_at }] }`, `own`: uploaded by the caller); `POST /attachments/:dataset/:id?kind&name` takes the raw bytes as `application/octet-stream` (else 415 `bad_content_type`) with a `Content-Length` and no `Transfer-Encoding` (411 `length_required`), at most `max_mb` (413 `body_too_large`), a declared kind (400 `bad_kind`) and a name of 1 to 200 characters without control characters or direction controls (400 `bad_name`), 30 uploads per account per minute (429 `rate_limited`), every one of these and the record and write checks decided before a byte of the body is read, and answers 201 `{ id, kind, name, mime, size, revision: { batch_id } }`; `GET /attachments/file/:id` answers the bytes; `DELETE /attachments/file/:id` soft-deletes it (`{ id, revision: { batch_id } }`). Reading needs reading the record in the caller's scope, plus `owner_visible` for an owner (a user or a link account); writing needs a dataset with a writer, plus `owner_writable` for an owner, who deletes only its own uploads (403). Every failure to read a file is the same 404 `unknown_attachment`. Only pdf, jpeg, png and webp are taken, judged by their first bytes, never by the name or the client's type (415 `bad_file_type`); the stored type is the judged one. A file is served with `Content-Disposition: attachment` (inline for the image types) and an RFC 5987 `filename*`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox` and `Cache-Control: private, no-store`. An upload and a delete are each revised under one `write` batch and undone as Revision says. `/schema` serves `attachments: { kinds, max_mb, owner_visible?, owner_writable? }` on each dataset that declares them, to an owner only with `owner_visible` |

**Source display.** The engine's `source_display` table holds, per source name, an administrator's label and icon over the declared ones (`PUT /sources/:name/display`, administrator only, `{ label?, icon? }`: a label of 1 to 60 characters, an icon from the fixed set, null restoring the declaration). `/schema` serves the override for the sources the caller can read. Each change is revised under a `write` batch and is not undone.

**Skins.** A source offers the skins it declares a need for, on datasets and queries alike: grid (stored as `table`; every source has it), calendar (on the calendar need, as today), board (on a lifecycle or option column), timeline (on the calendar need), gallery (on an attachment column) and dashboard (over several query views; see Dashboard). Matrix stays on a join dataset's down source, and list is the recipient page. In v1 every skin but the grid and the matrix is read-only: no drag, no editing inside the skin, an item opens its row. Table (the grid), matrix (one relation across, one down, cells are the join rows), calendar (month and week, rows placed on the declared `calendar.day`, grouped by one declared lane; read-only in v1: no drag, no create from a cell, an event opens the row), list (the recipient page), board (cards grouped by a declared lifecycle column; moving a card is a lifecycle transition). Board, timeline, gallery and dashboard are built in step 3c; none knows a domain word. Matrix rule for open slots: when the matrix declares `open`, join rows whose across relation is null are shown in one leading "open" column per row, as the sum of their `count` with their `match` labels; choosing an entity in an open cell asks for the `match` value first when the row's open slots have more than one, then runs the `fill` action on one open row of it with the entity as input, under one batch that one undo reverses. The domain's action decides how a slot is filled; the engine knows no split rule. Drag and drop is not in v1. When the domain declares a label column, join rows with a free-text label instead of an entity get their own columns under an "extern" group.

**Dashboard.** The command centre: the page a planner opens first and comes back to all day. It answers three questions without a click — what is wrong now, what happens this week, what waits on me — and every answer is one click from the view that fixes it, in the grid's own visual language.

- A dashboard is an aggregated skin: a saved view with skin `dashboard`, no source, and its layout in a `layout` column of its own. It names its tiles in sections; every tile reads one existing saved view through the existing rows route under the caller's scope, and it stores nothing else. Composition is the view update route; sharing, the rail and the owner refusal come from the view machinery. A dashboard has no source and every other skin has one; its layout is validated against the views it names and capped (6 sections, 12 tiles each, 8 quick actions). It can be neither public nor for owners.
- Tile kinds, all generic: a **stat** (one number from a view: its row count or one column's sum, toned by a declared badge or threshold so conflicts above zero read red; beside it, the same number over the previous period as the change, where the view has a date condition); a **list** (the first N rows of a view, its title and a few columns, its row actions inline, "Alles tonen" to the view); a **week strip** (a calendar view in seven columns, today marked, each event opening its row); a **progress** (a count against a total from two views: slots filled of slots open).
- Quick actions in the header: a create on a named dataset or a declared dataset action, run through the existing action routes with the inputs dialog the grid uses; keyboard reachable.
- The space switcher applies: a dashboard shows the chosen space record or all of them.
- Administrators compose it in place (sections, tiles, which view, which kind, order); the domain seeds a dashboard as it seeds any view, its tiles naming seeded views by name. A shared dashboard is seen by editors and administrators like any shared view, and never by an owner. It refreshes on focus and after any action it ran. The rail's first item is Dashboard, and the grid opens on the first dashboard view the caller can read.


**Sidebar.** The grid's sidebar is a tree of the datasets the caller can read, in the domain's sections, each with its saved views under it and then the views of every query declared `of` it (marked as computed); a query without `of`, or whose `of` the caller cannot read, is a node of its own, and at its top a switcher over the domain's space (theatre: productie). A space narrows what a planner sees and never limits what they may read: the grid adds the selected record to the rows filter it already sends, and the engine never filters by space. The period is a condition on the declared date column (deze week, volgende week, deze maand, ligt tussen), stored in the view like any other condition; a table sends it in its filter, a matrix reads the condition's days, else the current week. A link carries a view's conditions as `#view=<key>&f=<json>` (and `&j=or` for Of); they land once in place of the view's own, unsaved, and a condition the view cannot hold is dropped.

**Lifecycle.** A dataset may declare a lifecycle on one options column (`LifecycleDecl`: `{ column, transitions: [{ from, to, roles, label? }], hooks?, token_projection? }`, `from` a list of options or `*`, every role listed explicitly, `label` the transition's verb as the domain names it, a non-empty string, shown on the action token's page). A write that changes the column on an existing row, through PATCH, an action's update or undo, is a transition, allowed only when a declared transition matches the current and the new value for the actor's role; otherwise 422 `transition_not_allowed`. A create is not a transition: it may set any option, and the writer still judges it. A write may carry `expect: { <column>: <from> }`; inside the write's immediate transaction a mismatch with the current value is 409 `transition_lost`, so two people cannot both win. The grid sends the value it showed; a write without `expect` is judged on the current value, except that a service account's PATCH naming the lifecycle column without `expect` is 400 `bad_body`. `expect` is therefore a reserved column name. Undo checks in an undo mode: only the exact inverse of its own batch's transition, behind `changed_since`. Every transition appends to Revision with from, to and actor. Hooks are declared per state and return data, never do I/O (`HookResult`: an action token to mint, a mail, a notice for the write's reply); they fire on entering a hooked state, by a transition or by a create through `POST /rows` or an action, never through import, `--seed-missing` or undo. The token is minted inside the transaction; the mail goes through the Mailer after commit, so a write that rolls back sends nothing; an undo revokes the action tokens its batch minted. `/schema` serves `lifecycle: { column }` per source. `/schema` serves `record_link: true` on a dataset declaring `record_link`. A lifecycle is opt-in: a status column without one stays a free enum. Grids hide no transition: they send the write and show the server's refusal, and the server is the authority.

**Record links, action tokens and public create.** Two token shapes, never one. A **record link** is a stable link to one record of a dataset declaring `record_link: { email? }`: `<dataset>.<id>.<base64url HMAC-SHA256>` over the dataset, the id and a version kept in the engine's `record_link` table, keyed with a secret file (`--link-secret-file`: at least 32 bytes, refused when group- or world-readable, never in the database, never logged; startup refuses a domain declaring `record_link` without it), at most 128 characters. Nothing is stored per link: an administrator re-copies it at any time (`GET /record-links/:dataset/:id`), rotating bumps the version (`POST /record-links/:dataset/:id/rotate`), revoking is rotating without handing the new link on, and undo never touches the table. The page is `<app-url>/#/link/<token>`; it keeps the token in memory and sends `Authorization: RecordLink <token>`, and the holder acts as the record's link account, which reads the views for owners and nothing else. Verifying reads the live record and its version on every request; every failure, a missing record included, is one identical 401 `bad_link`. `POST /record-links/request { email }` mails the current link to each live record whose `email` column matches, with one identical answer for every address, delivery after the response, and nothing written; 20 per client address and 5 per email per 15 minutes. Only a human administrator changes the column `record_link.email` names (403 `forbidden` for anyone else, a service account included); a change rotates the record's link and revokes the outstanding action tokens of its subject. Laika's person page is a record link. An **action token** is single-purpose: a lifecycle hook mints it for one record, the state just entered (`from_state`) and the states it may move to (`to_states`), with the record's owner subject stored at mint; 32 random bytes stored as sha256, compared in constant time, expiring, consumed on first use, and minting revokes the record's earlier tokens. The page is `<app-url>/#/act/<token>`; `POST /act/view { token }` answers the lifecycle's `token_projection` (owner-visible columns, relations as titles, the lifecycle column as its option label), `labels` (the projection's column labels) and `to` (each allowed state with the label of its transition from `from_state`, else its option label) and `POST /act { token, to, values? }` consumes the token and makes the transition in one transaction, writing `values` (a plain object, else 400 `bad_body`; only `owner_writable` columns, else 403 `column_not_owner_writable` naming the first other key) in the same write and batch, with `expect` set to its `from_state`, as the stored subject's link account, on that record only. A bad, used, expired or reassigned token gets one identical 401 `bad_token`; a refused transition leaves the token unused. Both are public routes: failures counted per client address (20 per 15 minutes), no CORS header, the Host check and the write guard kept, and every response, a 401 included, sends `Cache-Control: no-store`, `Referrer-Policy: no-referrer` and `X-Robots-Tag: noindex`. A dataset may also declare one public-create action: an anonymous write that goes through the dataset's writer, rate-limited and with a honeypot field, and returns only the token. Nothing else is open to anonymous callers.

**Delivery.** A published SavedView renders per recipient, writes a Publication, and sends by channel. The same `share_token` serves html, ical and pdf through `format`. The recipient page shows the rows, the location block from any related dataset flagged for it, and — when the domain declares an actual side on a dataset — the confirm-and-correct controls for it.

**Access.** Four actors, no domain words. Administrators, editors and owners are engine accounts holding one of three engine roles, each account of one kind: `user` signs in by magic link, `service` is an agent authenticating by Bearer token, and `link` is the internal actor row of a record link's or action token's holder, created on first use, which never signs in. Recipients act through share tokens and need no account.

| Actor | Mechanism | May |
| --- | --- | --- |
| Administrator | engine account with role `administrator`, of kind `user` or `service` | Everything: Field, publish a query view with a share token or for owners, change a public or for-owners view, re-copy and rotate record links, rename a source or change its icon, and what writers reserve to administrators. A service account may not publish, publish for owners, or re-copy or rotate a record link (403) |
| Editor | engine account with role `editor`, of kind `user` or `service` | Read and write every dataset and query that a writer does not restrict; own SavedView rows only; no publishing |
| Owner | engine account with role `owner`, of kind `user` or `link`, linked to a row by `(subject_dataset, subject_id)` on the engine's own account table | Read only rows whose owner column is its subject, and see only the sources that declare one (any other source is 404); write only what the source's writer allows, scoped to its own rows; no SavedView writes (403 `forbidden`). A link account reaches `GET /auth/me`, `GET /owner/views…`, `PATCH /rows/:dataset/:id`, `GET` and `POST /attachments/:dataset/:id` and `GET` and `DELETE /attachments/file/:id`, matched by method and path, and nothing else: every other route is 403 (no create, no delete, no `/actions`, no undo). Its `PATCH` writes only `owner_writable` columns of rows in its scope (any other key 403 `column_not_owner_writable`, naming it, checked before the writer) and answers `{ id, revision }`, never the row; besides that it writes the transition its action token makes, with `values` beside it. An owner of kind `user` keeps the rule above: its writer decides which columns. An owner of kind `user` still reads whole rows of its sources; cutting it to owner-visible columns is a later step |
| Recipient | `share_token` of a SavedView or Publication, or no token for a declared public-create action | Read-only rendering of that view or snapshot, in its `format` |

Laika's core team become editors. An owner account with no subject sees nothing. An owner column given any value other than the subject is 403 `forbidden`, on create and on update. Every request re-reads the account, so a changed role or a disabled account takes effect at once. The engine knows roles only as this table; who may write which dataset stays in domain writers.

Sign-in is a magic link: `<app-url>/#/auth/<token>`, the token in the URL fragment so it never reaches a log or a scanner's GET. The grid's confirm page shows one button, which POSTs `{ token }`; consume is a guarded write, single-use, valid 15 minutes. A request for a link answers the same `200 { ok: true }` whatever the email, and delivery happens after the response. Link tokens and session ids are stored only as sha256. Every sign-in mints a new session id (30 days; cookie `wt_session`, `HttpOnly; SameSite=Lax`). Rate limits: link requests 5 per email and 20 per client address per 15 minutes, consume 20 per client address per 15 minutes, answering 429 `rate_limited`; proxy headers are never trusted. In 0e accounts are managed by the engine CLI (`--create-admin`, `--create-account <email> --role <r> [--subject <dataset>:<id>]`, `--disable-account <email>`); there are no account routes. Only kind `user` gets magic links and sessions. A service account is made by `--create-service <name> [--role editor|administrator]` (editor unless given; its name unique, no email), which prints its token once and stores sha256 of it; `--rotate-service <name>` prints a new one and `--disable-service <name>` sets `disabled_at`, each taking effect on the next request. It sends `Authorization: Bearer <token>`, which wins over a cookie; every failure is one identical 401, 20 per client address per 15 minutes, and an account makes at most 600 requests per minute. Its writes carry its id, history names it, and it undoes its own batches and no one else's. `GET /schema?format=openapi` answers an OpenAPI 3.1 description generated from the caller's own readable sources; without `format`, `/schema` answers as before. With no mailer, a link goes only to a development outbox (`--outbox <dir>`) and a non-loopback `--hostname` is refused at startup. Real mail delivery, `Secure` cookies and a trusted proxy are the cutover's. Behind a proxy every request arrives from one address, so the per-address limits (`/act`, record links, `/owner`, Bearer failures) become global ones: a trusted-proxy client address, or failure limits keyed by token as well, is a cutover precondition before real persons reach `/act` or `/owner`.

The engine rejects any request whose Host is not its bound address; this check stays when auth lands. Writes require a JSON content type, and a browser request must be same-origin: `Sec-Fetch-Site` `same-site` or `cross-site` is refused, and so is a request that carries an `Origin` without `Sec-Fetch-Site`; this check also stays when auth lands. From step 0e on, the permission check runs before the in-use check, so an actor who may not delete gets a refusal without the in-use counts; a test proves the order. Behind a dev proxy that rewrites the Host (the grid's Vite server), the proxy's own host check stands in for the engine's, and it is pinned in configuration, never left to a default.

Scoping is declared, not coded: a dataset or query names an owner column for the owner role (person, customer, courier and so on), and the engine filters by it. Writers receive the actor and may refuse on it; `refuse()` rules stay domain. Action links (confirm, decline, register) are single-purpose tokens with an expiry, never a sign-in.

**Custom fields.** Keys are addressed `entity.key`, never flattened. A query passes each joined dataset's `custom` through as its own column (`persoon_custom`, `activiteit_custom`); the grid flattens them using Field. Filters compile to `JSON_EXTRACT`; a hot key gets an expression index, not a schema change.

**The one refusal.** Admins create fields, views, templates and publications — never datasets. A dataset is code in a domain package. That line is what keeps this an engine for many clients rather than another NocoDB.

## The contract

A domain package implements exactly five things. If it needs a sixth, the engine is missing a shape, not the domain a feature.

1. **Datasets.** One declaration per table: columns, relations, indexes, an owner column for the owner role, an optional lifecycle with its action token's projection, an optional record link, the columns a view for owners may show, whether it carries `custom`, and which parent relation Attachment and custom values inherit along.
2. **Queries.** One SQL file per view plus its column map. Every query exposes an `id` column, so each row has an identity. The SQL joins datasets, other queries and the engine's generic tables. Each column either reads or declares its write target.
3. **Writers.** One module per dataset with create, update and delete, free to refuse. The rules that live in atelier's PHP repositories today — one of person or name, one assignment per person per activity — move here as they are; the classes do not. Domain rules live here and nowhere else.
4. **Skin needs.** Which column is the title (or a title through a relation, `{ via, else }`), which column is the date for calendar, the matrix declaration on its join dataset, which status column the board groups on. One line each.
5. **Seeds and parameters.** Sjabloon rows, Rol rows, the organisation's day-line hour and working-time limits — all data seeded by the package, editable by the admin.

What a domain package does **not** contain: grid components, saved-view logic, publication, share links, audit, custom-field rendering. Those belong to the engine, once.

**The test.** The VAD Doorverwijsgids is a second domain: one `fiche` dataset with `custom`, two or three queries, one writer, no Publication. It has to run on the same engine with zero engine changes. If it needs one, the engine learned a name it should not know, and that change is reverted into a shape.

**Package layout.** One new repository, `worktable`, for the whole system: `packages/engine` (shapes, REST, views, publication, actors; imports no domain), `packages/theatre`, `packages/fiche` (the Doorverwijsgids, kept in the repo from the first week as the test that the engine knows no theatre word) and `apps/grid` (the React grid). A lint check in the gate fails any import of a domain package (`theatre`, `fiche`) from inside `engine`; domain packages import `engine` to register their shapes. A second check fails any domain word anywhere in `packages/engine`, in code, comments and tests. Its word list is built from the domain packages' dataset, query and column names, plus a fixed list of the spec's domain nouns. A committed allowlist, one word per line with its reason, names the generic English words a domain also uses (`status`, `type` …). A third check fails any term from the export's name list, kept on the owner's machine outside the repo, in the staged diff; without the list it is skipped. It starts clean, not inside Folio: Folio is an agent case tool of about 26,000 server lines, and only its filter compiler, its views and fields table shapes, its magic-link sessions, and its board drag and rank (Stefan, 2026-10-14: the drop resolution and the rank between two neighbours, less the slot line it draws on a sorted board's cross-column drop, Folio's `apps/web/src/components/views/kanban-view.tsx:325-336`, and less its skipping of unranked neighbours, which puts a card moved down in an unranked column first, `apps/web/src/components/kanban/board-reorder.ts`) are worth copying in. Domain packages are TypeScript modules the engine loads: the theatre package holds its declarations, SQL views, writers and seeds. WordPress keeps its own atelier package for public content and gains one small client: one shortcode and YOOtheme element that render a public view by a site-side name: `[worktable_view view="<name>"]`. The site's configuration maps each name to the view's share token, so a token never reaches post content, revisions or WordPress's REST API, where YOOtheme's stored layout would publish it. The fetch is server-side, cached five minutes per engine, token and window, and stops for a minute when the engine is down or rate-limited. Nothing of the engine lives in PHP.

Step 3f adds five shapes and nothing else (Stefan, 2026-10-14, after the step 3e preview: the board's drag "like Folio", and yes to the four held questions Q1, Q2, Q6 and Q11; settled with the orchestrator 2026-10-15, `specs/step-3f/brief.md`):
- **`position`** on every dataset table: an engine-managed nullable text column, a rank compared as plain strings over the base-62 alphabet `0-9A-Za-z`. A new rank always falls between its two neighbours and is never rebalanced. The rows route sorts on it with nulls last: ranked rows by rank, then the unranked ones by the sort's other keys, then id. A rank is at most 255 characters of `0-9A-Za-z` and never ends in `0` (no rank can be placed beside one that does); anything else is refused. A domain may not declare a column, lookup or link named `position`, as it may not name one `id`. It is written like any edit: through the writer, with a revision, undone by one ⌘Z. An owner account never writes it. It is sortable over REST, never filtered, grouped or in a Publication; the rows route serves it, and the grid computes a new rank from the two neighbours' ranks, as Folio does; history lists a change of it as a move, never its rank; `/schema` marks it sortable on each dataset. A query has no position. A board in manual order sorts on `position` first: the view's sort is `[{ id: 'position' }, …its previous keys]`, so the unranked cards keep the order they had. A drop ranks the still-unranked cards above its slot, and any ranked card above it out of order, in their shown order, then the dropped card last, each with a fresh rank above the last ranked card before it, so nothing on the board moves but the dropped card; each is its own write, and one ⌘Z undoes them together. The display is optimistic: when the dropped card's write is refused it snaps back, and the ranks already written stay, since they encode the order shown. A refused drop leaves no undo step; the ranks it wrote match the order already shown. When a board switches to manual, a card whose rank disagrees with the order shown has its rank cleared in the same step, so nothing moves but the dropped card; ranks outside the window shown stay. A within-column drop on a sorted board switches the view's sort to manual; on a locked or standard view that switch stays in the planner's own layout, with the "changed" mark. The rank write itself is a record edit everyone sees. A drop that changes a card's column and its place writes both in one write, under one batch. The drop indicator shows where the card will land: on a sorted board, a drop into another column highlights that column, draws no slot line, lands the card at its sorted place and leaves the sort as it was (Folio draws a line there and lands the card elsewhere, `kanban-view.tsx:325-336`); on a board over a query, a within-column drop draws no line and does nothing.
- **`long: true`** on a text column (Q1): the grid edits it as long text, and the record drawer shows it as its own block. Theatre: activiteit's notities.
- **`flags`** on a query (Q2): `flags: { marks: { <dataset>: <integer column of the query holding that dataset's ids> }, tone: <options column with tones> }`. Each row of the query flags the rows its marks point at, with its title column as the text and its tone column's tone. The grid reads them through the rows route in the caller's own scope, so a caller who cannot read the query sees no flags; the engine validates the declaration and serves it in `/schema`, and nothing else. The grid marks the flagged cards, bars, events and cells; the title line shows how many of the view's rows are flagged, with the query's label, as a button that opens the query's view in the same space. The record drawer shows a flag as a band with "Iemand anders kiezen" and "Negeren". "Iemand anders kiezen" shows only where the flag marks a row of one of the record's links whose target column declares `options_from`: it opens that row's picker in the record's link section, listing its candidates, and a pick is an edit of that row, undone by one ⌘Z. "Negeren" hides the band in the open drawer and stores nothing, like the cell drawer's "Toch laten staan". Filling an open place and adding one from the drawer stay deferred. A lasting dismissal would need a stored acknowledgement the scope does not hold, so a flag ends when its rows change. The engine never knows what a flag means. Theatre: conflicten flags activiteit, toewijzing and speelreeks, toned by ernst. The timeline's "N overlap" is no flag: the grid counts the bars of one lane that overlap in time, leaving out the bars whose status is toned `bad`, marks them and shows the count in the title line.
- **`tone`** on a dataset (Q6): one of its options columns, every option of which carries a tone. The record takes that tone wherever it is a calendar or timeline lane, and on the card lines of the rows that point at it; without one, lanes take the palette by order. Theatre: a `kleur` select on productie.
- **`filled`** as a group fact (Q11): `{ kind: 'filled', link, label }`, read as "label have/need" over a group's rows, in places: an open item (neither a target nor a title) holds its `places`, every other item holds one, and an item whose state is toned `bad` holds none; have the places of the items that are not open, need those and the open ones. The links cell and the record drawer's link head show the same have/need; the drawer's list shows an open item for more than one place with "×N" beside it, and a refused or cancelled open item with its state. Theatre: "bezetting" over activiteit's mensen, counted by toewijzing's aantal (Stefan, 2026-10-17: "aantal"; an open "Speler ×2" is two places).

## Websites as consumers

A website is a page built on the engine's data, never a second tool. It reads through queries and published views, and writes only what one person may write about themselves. It holds exactly one of three credentials, chosen by the page:

| Credential | Fits | Reads | Writes |
| --- | --- | --- | --- |
| Share token | A public page: a performance calendar, a published schedule | The one view the token publishes | Nothing |
| Record link (or an action token) | A page for one person: their productions, their answer to an invite | That person's rows, through views for owners and owner-visible columns | That person's owner-writable columns and their own lifecycle answers |
| Service account | A trusted server-side consumer only, whose token never reaches a browser | Everything its role reads | What its role writes, logged as the account |

- A query a website reads is a published contract: its columns may only grow. A column is never renamed or removed while a consumer reads it; a change of meaning is a new column.
- The grid's `#/link` (the person page) and `#/act` (the invite answer) are the reference consumers: a website builds its own versions of those pages on the same routes and credentials.
- Closed as website work, not engine work (Stefan, 2026-10-12): the Doorverwijsgids detail template (a fiche's detail page is a website page reading the fiche through a public view), and cargo C1 (several owner columns), C3 (a dry-run quote) and C10 (administrator account routes).
- Cutover precondition: Laika's website needs an invite-answer page and a person page before real invites go out.
- Cutover skim: the 108 uitgenodigd rows the import created flag as onbevestigd from 2026-10-13 (their invite moment is the import date); a planner skims and cleans them before cutover. No code.

## Storage

The engine owns its data. One database per engine instance; nothing of the planning tool is stored in WordPress or read from it.

| Concern | Choice | Why |
| --- | --- | --- |
| Database | SQLite through Drizzle, as Folio does; Postgres behind the same schema when a client's size or hosting asks for it | Theatre-scale data is thousands of rows; SQLite handles it on one file, and both engines support the views and JSON functions the queries need |
| Datasets | Real tables with real columns, foreign keys between datasets, indexes per table: Activiteit `(plandag)`, Toewijzing `(persoon_id)` and `(activiteit_id)`, Attachment and Revision `((entity, record_id))`. persoon_dag joins across tables, so no index spans two | Every query is a join on a column; no pivot, no serialised id list |
| Migrations | Each dataset's DDL is recorded with its hash in `_migrations`. A changed hash is migrated: a new nullable or defaulted column and index changes by `ALTER`, anything else by SQLite's table rebuild, in one transaction with foreign keys off and `foreign_key_check` before commit. Ids and `sqlite_sequence` survive, Revision is never touched, and every query view is recreated after a change. Changes that would lose data are refused before anything is written, naming the dataset and column: a new NOT NULL column without a default on a table with rows, a lossy retype on a table with rows, and NOT NULL over a stored NULL. Before any rebuild, the database is copied to `<db>.pre-migrate`. | A declaration change never needs a hand-made schema, and a mistake costs one file copy back |
| Queries | SQL views created at startup from each query's `.sql` file in its domain package, each recorded with its SQL hash in `_migrations`; a changed hash drops and recreates the view, and every view is recreated after any dataset change | A view is the contract between a query and the grid; the grid reads it like a table |
| Custom fields | One `custom` JSON column per dataset, declared in Field, `json_extract` in filters, an expression index on a hot key | Real columns stay real; the admin never changes a table |
| Derived columns | `plandag` is the one that is stored, computed by the writer: from `start_at` and the organisation's day-line hour when the activity has a time, and equal to `datum` when it has none; it is declared readonly, so it is cut from write bodies and set only by the writer | Grouping and indexing on it is the whole grid; everything else stays computed in a view |
| Dates and times | `date` is `YYYY-MM-DD`; `datetime` is `YYYY-MM-DDTHH:mm` or `YYYY-MM-DDTHH:mm:ss`, the organisation's local wall-clock time with no zone; both must be real calendar values | The day line, the window and every comparison read these strings as they are |
| What was in WordPress | A one-off export from the private Laika repo to JSON, loaded by the engine's generic import command, with a `legacy_post_id` kept for one release; the table-rebuild migrator (built in step 0e) runs every declaration change, including the import's `legacy_post_id` | The existing Laika data moves once; after that the private CPTs are deleted |
| WordPress afterwards | A REST client. Atelier keeps the public content it has — productions, people, performances, credits, images — and gains one shortcode and YOOtheme element that render a public view by a site-side name (`[worktable_view view="<name>"]`); the site's configuration maps each name to the view's share token, so a token never reaches post content, revisions or WordPress's REST API. The fetch is server-side, cached five minutes per engine, token and window, and stops for a minute when the engine is down or rate-limited | The website shows the schedule; it does not own it |

**Rules.**

- The engine never calls WordPress. Direction of dependency is one way: websites call the engine.
- Tables and views are created by migrations the engine runs from the domain package's declarations; no hand-made schema.
- A row's id is the engine's; nothing in the engine assumes a post, a user or a WordPress capability. Actors are the engine's own (see Access).
- Backups are the database file plus the attachment store; one instance per client keeps them separable.

**Import format** (the contract with the Laika exporter):

```json
{ "worktable_export": 1,
  "source": "<free text, e.g. laika>",
  "datasets": { "<dataset>": [ { "legacy_id": 12, "<column>": "…", "<relation column>": <legacy id of target>, "custom": { } } ] },
  "checks": { "counts": { "<dataset>": 0 },
              "activities_per_week": { "2026-W41": { "<status>": 0 } },
              "assignments_per_person": { "<persoon legacy id> | \"naam\"": { "<state>": 0 } },
              "absences_per_person": { "<persoon legacy id>": 0 } } }
```

- Weeks are ISO weeks of the calendar date WordPress shows an activity on: its exported `datum`, which an activity without a time also has. They are counted per mapped status, so the comparison depends on no view's filter. The engine side counts the same way, by `datum` and `status` over live rows, and separately reports how many activities with a time the day line (`plandag`) moves to the previous day; an activity without a time is on its own `datum` and never counts as moved. That move is a known, intended difference, never a failure.
- Name-only assignments, with no persoon, count under the key `"naam"`. An absence counts once per row, not per day.
- Every dataset present must be a declared dataset, and every key a declared, non-readonly column, `legacy_id` or `custom`. Anything else is refused with its path.
- The exporter always emits `status`, so no row relies on a default.
- Value encodings: datetimes `YYYY-MM-DDTHH:mm`, local time, no zone or seconds; dates `YYYY-MM-DD`; booleans JSON `true`/`false`; legacy ids non-negative integers; a relation value is the target row's legacy id; `custom` is an object of flat values (text, number, boolean, null, or a list of those) whose keys match the filter pattern `^[A-Za-z0-9_]+$`. A row breaking the `custom` rule is refused and reported.
- **No export in git.** `bun run check` scans every file in the index, committed and staged, reading each from the index: an export's file name, a `.json` file with a top-level `worktable_export` key (or one that cannot be read as JSON), or any other non-source, non-docs file holding `"worktable_export"` fails. An invented fixture is exempt by its content, not its name: under `test/fixtures/`, named `invented-*.json`, parsing, with a `source` starting with "invented" and only `@example.test` addresses.

**Parity rule.** `bun run parity <export.json>` imports into a temporary database, signs an administrator in through the engine's own link flow, reads the engine's REST, and compares with `checks`. Its output (`specs/step-0e/parity.md`) holds, per check, pass or fail, the total compared and the number of mismatched keys, plus counts per dataset and the plandag shift: no ids, names or values. The parity gate runs only on the owner's machine and commits counts only.

## How it works

A planner's week touches every layer in a fixed order. Each step names what it writes and what it reads.

1. **Plan a block.** Create a Speelreeks under the Productie, locatie set once, and apply a Sjabloon. One batch writes the activities of every day with inherited locatie (and, from step 2, open Toewijzingen per role slot). Revision records the batch under one `batch_id`: one undo, kept in the browser tab's undo history of batch ids and undone on the server.
2. **Fill the slots.** In the Toewijzingen view (table or matrix) the planner fills each open slot with a person, and the kandidaten dropdown (from step 3) lists who can fill it, available and conflict-free. Assigning in the matrix pencils the person in as `voorlopig`; the move to `uitgenodigd` (or a create as uitgenodigd in the grid) sends the invite; the person confirms or declines from the action token's link, without signing in. Activiteit.status stays about the booking, Toewijzing.state about the person.
3. **Clear conflicts.** conflicten runs on every grid render and badges affected rows. The planner works the Conflicten view to zero on Monday morning.
4. **Publish.** From any view on persoon_dag, Publish for a period renders each recipient's rows (names, call times, custom fields and attachments flagged for publication, the location block from Organisatie), writes a Publication row with those rendered rows, and sends by channel. A venue as recipient gets its block in its own language. The share token also serves the same view as ical and pdf.
5. **Handle change.** Shift the block by a day. Revision logs it; wijzigingen_sinds_publicatie returns, per recipient, the rows that differ from their last snapshot. The next Publish sends only the diff and writes a new snapshot.
6. **Register and approve.** After the day, the person opens their link and confirms or corrects actual times on their own Toewijzingen, adds what they spent with a receipt as Attachment. Unplanned work becomes an activity with `bron = registratie` and a Toewijzing on it. The planner works plan_vs_werkelijk: approve, reject with a note, or edit. From approval on, werktijd, dagtelling and verrekening_periode read actuals; before it, the plan.

**Day line.** A 20:30 show that strikes until 01:00 is one planning day. `plandag` = date of `start_at` shifted by the organisation's day-line hour (default 05:00); an activity without a time is on its own `datum`. Every query groups on `plandag`, never on the calendar date.

**Inheritance.** locatie, custom values and attachments resolve Activiteit → Speelreeks → Productie, first set value wins. The grid shows an inherited value greyed and an own value solid, so the planner sees which rows move with the block. On Activiteit, locatie is an inherited lookup through the Speelreeks, so every view on Activiteit carries it; an edit sets the activity's own locatie and never the Speelreeks's.

**Writes through a query.** A cell edited in a view on persoon_dag carries `writes: {dataset: toewijzing, field: state, key: toewijzing_id}`; the grid sends `PATCH rows/toewijzing/{row[key]}` and the engine routes it to the theatre package's Toewijzing writer, which applies its refuse rules. The query never writes; the writer always does. The returned row and the undo key refer to the target record, not the grid row.

## Principles and build order

Seven rules decide every design question. Everything above follows from them.

1. **Shapes in the engine, names in the domain.** The engine never learns a domain word; a second domain runs with zero engine changes.
2. **Datasets, queries, views.** Tables with rows; SQL views over them that store nothing; saved views over either.
3. **Slot first, person later.** A Toewijzing is a role on an activity; the person is filled in when known.
4. **Inherit down the tree.** Location, attachments and custom values set on a parent apply to children unless overridden.
5. **Plan and actual on one row.** No timesheet or expense table; the difference is a query; downstream numbers read the actual when it exists.
6. **Publish snapshots, not pointers.** Rendered rows with names, per recipient; the diff is current minus last snapshot.
7. **JSON plus registry for custom fields.** Real columns stay real; one `custom` JSON per table, declared in Field, passed through queries.

**Build order.** Each step is usable on its own and the next depends on it.

## Open decisions

Settled in this document, so they do not reopen:

- The engine is a standalone TypeScript service with its own database; WordPress is a REST client and holds no engine code.
- Day line: an organisation parameter, default 05:00.
- Conflicts are badges everywhere, `locatie_dubbel` included; nothing blocks a save except a writer's refuse.
- Invites and actions go by email carrying a single-purpose link; no app and no sign-in. A confirmation is made as the person's link account, an internal actor row the engine creates on first use so that Revision, batch and history name the person; it never signs in, gets no session and has no undo route.
- The matrix skin's first use is Toewijzing scoped to one Speelreeks: people across, activities down.
- The engine and its domain packages live in one new repo named `worktable`; the earlier markdown-records repo of that name is renamed `worktable-v0` and archived. Folio stays what it is and may later be a client of the engine.
- No Performance in the engine; websites read the `voorstellingen` query.
- Lifecycles, record links and action tokens, public create, owner columns and the board skin are engine shapes, added after a paper test of cargovelo-core against this spec. A `cargo` package for cargovelo-core is a candidate third domain and is not built in v1. Lifecycle, record links and action tokens are built in step 2; the board skin in step 3c; public create when a domain first needs it.
- Engine names are English (Field, SavedView, Revision, Publication, Attachment; skins table, calendar, matrix, list, board); the theatre package keeps Dutch names; UI labels are localised.
- This file, `docs/SPEC.md` in the worktable repo, is the spec of record; the Claude Doc it was written in is a snapshot.
- One engine instance per client, one database file each; multi-tenant hosting is out.
- Child spaces, resources, run-of-show: out, see Scope lock.
- Laika's core team get engine accounts with the editor role (step 0e); record links for owners come with step 2.
